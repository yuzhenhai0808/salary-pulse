该仓库用于核实同类产品的功能形态，不能据此认定它就是用户在社交平台看到的原始作者，也不能认定它已经支持 macOS。本文未运行该程序，也未审计其源码。

该参考 README 声明 MIT，但读取根目录 `LICENSE` 的链接时返回 404。若后续要复制任何代码或资源，应进一步核对对应版本的实际许可证、作者声明和资产授权；不能只凭 README 的一行声明完成合规判断。

### 1.3 “仿照”的含义

本项目借鉴的是功能模式和情绪体验，不直接复制他人的名称、界面、角色、音频或代码。

| 可以借鉴的产品思路 | 本项目自己的实现 |
| --- | --- |
| 工资数字随时间变化 | 可解释、可测试的本地工资估算引擎 |
| 角色陪伴和趣味动作 | 原创角色、独立素材和状态机 |
| 下班前获得情绪反馈 | 下班倒计时、鼓励语、可选通知 |
| 桌面小工具常驻 | Mac 菜单栏、可选悬浮窗、低干扰模式 |
| GitHub 下载或自行构建 | 源码、构建说明、双架构安装包和版本发布 |

建议内部工程名保持 `salary-pulse`，面向用户暂用“上班鼓励器”。“牛马”可以作为自选幽默主题，不应让所有用户默认接受带贬义的文案。

### 1.4 明确不做的内容

首版不做公司考勤系统、员工监控、真实工资结算、个税社保计算、银行到账查询、雇主后台、账号系统或云同步。

不读取键盘输入、屏幕、摄像头、聊天记录或公司文件；不根据键鼠活动判断用户是否“认真工作”。显示的收入是个人设定下的时间估算，不是工资凭证或劳动法结论。

## 2. 产品定位与使用场景

### 2.1 一句话定位

一款放在 Mac 菜单栏或桌面边角的小工具：展示工作时间内的估算收入、距离下班的时间，并通过原创角色和个性化鼓励语提供轻量陪伴。

### 2.2 核心用户

- 有相对固定上下班时间的个人用户。
- 希望看到时间流逝带来的正向反馈，但不希望使用复杂效率工具的人。
- 想在自己 Mac 上使用、改主题、改文案，或者从 GitHub 构建程序的用户。

首版优先支持固定排班；灵活工时和手动计时作为后续能力，避免混淆“按排班估算”和“按实际开启时长计时”。

### 2.3 典型使用流程

1. 从 GitHub Releases 下载 DMG，将 `.app` 放入“应用程序”；开发者也可从源码构建。
2. 首次启动时可以切换中文/英文，填写月薪或时薪、工作日、班次和休息时间。
3. 选择是否在菜单栏显示金额、是否打开悬浮窗。
4. 工作时看到金额、倒计时和角色状态；午休时角色休息。
5. 到达下班时间时收到可选通知，下班后停止本班次估算；提前提醒属于 P1。
6. 下一次打开程序时配置仍在，金额按当前排班时间重新计算。
7. 可以随时隐藏金额、关闭动画、停用通知，或者彻底退出程序。

### 2.4 产品成功标准

- 用户不需要 Node.js、Rust、数据库或服务器即可使用发布版。
- 填好设置后，关闭窗口、休眠、重新启动不会导致收入计数重复或丢失。
- 菜单栏、主窗口和悬浮窗展示同一份计算结果。
- 断网仍能运行全部核心功能。
- 同一安装包的中文和英文界面都完整可用，切换无须重启，重启保留选择。
- 常驻后对办公性能和电池的影响足够低，并通过实际测量确认。
- 私人薪资不会因为截图、通知、日志或 Git 提交而被默认泄露。

## 3. 功能范围与版本规划

### 3.1 优先级定义

- **P0 / MVP**：第一份可在个人 Mac 上长期使用的完整版本，建议发布为 `v0.1.0`。
- **P1 / v0.2～v0.3**：增强趣味、提醒、统计和备份功能。
- **P2 / 后续**：需要明显额外成本，只有出现实际需求才开发。

“MVP”不等于只做网页。它必须包含桌面入口、配置保存、计算引擎、基本互动、Mac 打包和必要测试。

### 3.2 功能清单

| 功能域 | P0 必须开发 | P1 增强 | P2 可选 |
| --- | --- | --- | --- |
| 薪资配置 | 月薪、时薪、币种、折算参数 | 年薪、周薪、多组薪资方案 | 复杂薪酬组成 |
| 时间配置 | 固定周排班、跨午夜班次、带薪/无薪休息、手动日期例外 | 轮班模板、可信离线节假日数据 | 外部日历订阅 |
| 实时展示 | 本班次/今日估算、下班倒计时、当前状态 | 本月估算、目标进度、趋势 | 高级分析 |
| 桌面入口 | 菜单栏、主窗口、单实例 | 菜单栏快捷切换内容 | 系统 Widget |
| 悬浮窗 | 显示/隐藏、拖动、置顶、位置保存 | 透明度、多种布局、点穿 | 桌面贴纸系统 |
| 角色与鼓励 | 原创角色、工作/休息/下班状态、一项点击互动、文案轮换 | 听歌、如厕、奖励、主题包 | 复杂 3D、角色编辑器 |
| 个性化 | 昵称、幽默/温和文案、深浅主题、隐藏薪资、减少动画 | 自定义文案和资源导入 | 社区主题商店 |
| 语言 | 简体中文、英文、跟随系统、即时切换、选择持久化；界面/菜单/通知/内置鼓励语完整覆盖 | 经需求确认再扩展其他语言 | 社区翻译协作平台 |
| 提醒 | 下班提醒、权限状态、静默与去重 | 喝水、休息、站立、生日提醒 | 智能提醒策略 |
| 数据管理 | 本地保存、版本迁移、损坏恢复、删除个人数据 | 导出/导入、历史统计、加密备份 | 多设备同步 |
| 系统集成 | 默认不开机自启、可选启用、正常退出 | 全局快捷键 | 辅助功能集成 |
| 发布 | Apple Silicon / Intel 双语 DMG、双语安装说明、校验和；公开正式版必须签名公证 | 可选更新检查与自动发布 | 自动更新、Homebrew Cask |

说明：签名公证对于“仅自己从源码运行”的 MVP 可以暂缓；对于面向普通用户的公开正式发布，应在发布前完成。这里的优先级不意味着可以把未知安装包的安全警告当作无关紧要的问题。

### 3.3 P0 详细验收口径

| 编号 | 需求 | 完成条件 |
| --- | --- | --- |
| F01 | 首次配置 | 不填薪资不能开始；可随时返回修改；错误定位到对应字段 |
| F02 | 金额增长 | 工作区间内按有效计薪时长增长；午休规则可解释 |
| F03 | 下班倒计时 | 达到下班时间归零，不出现负数；下班后切换状态 |
| F04 | 排班例外 | 能把指定日期标记为休息或额外工作日；冲突有提示 |
| F05 | 本地持久化 | 重启后配置保持；修改失败不显示“已保存” |
| F06 | 菜单栏 | 点击打开面板，菜单含设置、悬浮窗、隐私和退出 |
| F07 | 悬浮窗 | 不强制出现；拖动位置保存；屏幕变化后仍可找回 |
| F08 | 趣味反馈 | 三种基础状态有视觉差异，互动不改变真实估算速率 |
| F09 | 下班通知 | 用户主动授权；同一班次最多一次；拒绝后不反复弹授权 |
| F10 | 数据保护 | 通知默认不含薪资，隐私模式覆盖所有金额显示 |
| F11 | 正确恢复 | 合盖和重启后重新计算，不依赖休眠期间定时器运行 |
| F12 | 发布可用 | 两种 CPU 架构产物有标识，至少完成对应实机/可用环境验证 |
| F13 | 中英切换 | 首次设置和设置页均有语言选择；已有窗口、菜单、新通知与鼓励语无须重启即可切换 |
| F14 | 语言保持 | 选择存入本地配置，重启、升级、断网后仍有效；保存失败明确提示且不假称持久化 |
| F15 | 本地化完整 | 中文/英文翻译、按钮提示、表单错误和无障碍标签均覆盖；CI 检查缺键与占位符 |
| F16 | 计算不受语言影响 | 切换语言只改呈现，同一时刻金额、币种、时区、班次 ID 与通知去重 ID 不变 |

### 3.4 首版不引入服务端

不需要 Spring Boot、FastAPI、Docker、PostgreSQL、Redis 或云主机。GitHub 负责源码托管和分发，不是应用运行时后端。

如以后需要云同步，应作为单独项目阶段重新设计账号、端到端加密、费用和服务故障处理，不能把薪资数据默认上传。

## 4. 页面与交互设计

### 4.1 界面组成

| 界面 | 主要内容 | 交互与约束 |
| --- | --- | --- |
| 首次设置 | 语言、昵称、薪资、折算口径、排班、隐私偏好 | 开始填表前即可切换语言；不清空已填内容 |
| 主窗口 | 估算金额、倒计时、原创角色、鼓励语、快捷动作 | 一屏完成常用操作，不做营销落地页 |
| 菜单栏面板 | 状态摘要、紧凑金额、剩余时间 | 固定宽度，内容不因数字位数跳动 |
| 悬浮窗 | 单个金额或倒计时、简化角色 | 默认不抢焦点，不遮挡大量办公内容 |
| 设置页 | 语言、薪资、排班、日期例外、角色、通知、系统、数据 | 语言选择立即保存，不顺带提交未保存的薪资草稿 |
| 统计页（P1） | 日/月估算、来源口径、休息与互动统计 | 不把估算称为实际到账；缺失数据不伪造 |
| 关于页 | 版本、项目地址、协议、资源致谢 | 明确开源项目与隐私说明 |

### 4.2 建议窗口尺寸

- 主窗口初始约 `760 × 520`，最小约 `640 × 460`，最终根据文本布局验证。
- 菜单栏面板约 `340 × 320`，在屏幕可用区域内定位。
- 悬浮窗约 `240 × 120`，支持收起；金额采用等宽数字和固定宽度。
- 首版使用原生窗口外框或 macOS 标题栏；不要为了“像截图”立即重做所有系统按钮。
- 输入框、图标按钮、数值控件要有稳定尺寸；大字体只用于金额和倒计时。

以上是设计起点，不是硬性适配保证。必须验证 Retina、缩放显示、较小屏幕、较长中文昵称、英文文案和大额金额；英文通常比中文占据更大宽度，不能仅按中文设计固定高度。

### 4.4 主要交互规则

- 点主窗口关闭按钮：隐藏到菜单栏；首次发生时给一次简短提示。
- 菜单“退出”或 `Cmd+Q`：真正退出，停止所有线程，不留后台进程。
- “隐藏金额”：主窗口、悬浮窗和菜单栏同时隐藏金额；状态和倒计时仍可见。
- “隐藏窗口”：只影响展示，不停止按排班进行的估算。
- “角色休息”：只是趣味状态；是否计薪由排班规则决定，不由动画决定。
- 不默认播放音频、不默认发送系统通知、不默认注册全局快捷键。
- 设置有未保存修改时离开页面，询问保留或放弃；保存使用版本校验，防止多窗口互相覆盖。
- P0 没有“暂停工资”按钮。若 P1 增加手动计时，必须独立标识，不能混用两种口径。

### 4.5 动画与素材策略

首版使用一套原创 2D 位图角色或已明确授权的资源，至少包括工作、休息、收工三种状态，以及一项点击反馈。

- 可用 PNG/WebP 帧序列、精灵图或经过验证的 Lottie 文件。
- 普通 UI 用 CSS 过渡，角色复杂动作由状态机触发；不把整个应用做成高帧率画布。
- 状态资源尺寸固定，加载失败时显示静态占位，而不是空白。
- 所有资源随安装包携带，离线可用；README 展示截图使用演示薪资。
- “减少动态效果”开启时使用静态图；隐藏窗口停止角色动画。
- 若加入音乐，使用原创或合法授权音频，保留授权记录，默认静音。
- 不复制参考产品的角色、胡萝卜、音频或标志性组合视觉。

### 4.6 中英文切换与本地化设计（P0）

#### 4.6.1 范围与交付方式

用户要求的“两个语言版本”采用**一个双语程序、同一安装包内切换**，不制作两个独立应用，不复制工程，不创建两份用户配置。

- 首版支持 `zh-CN`（简体中文）和 `en-US`（英文，采用美式英文文案）。
- “中文”目前按简体中文设计；繁体中文文案不是本次已确认范围，若需要再增加 `zh-TW` 等资源。
- Apple Silicon 和 Intel 各一个 DMG，每个 DMG 都包含完整中英文资源。
- 语言资源全部随包携带，不需要下载语言包，不调用在线翻译服务。
- 中文界面名称暂为“上班鼓励器”，英文界面名称为“Salary Pulse”。
- 应用文件名、应用标识、配置目录和版本号固定，切换语言不创建第二个应用或数据目录。

#### 4.6.2 默认选择与回退

语言选择使用菜单/选择控件，提供以下三个选项，显示语言自身的名称，方便用户在看不懂当前界面时找回：

| 配置值 | 选择项 | 含义 |
| --- | --- | --- |
| `system` | 跟随系统 / System | 按 macOS 首选应用语言或首选语言列表解析 |
| `zh-CN` | 简体中文 | 用户固定选择简体中文 |
| `en-US` | English | 用户固定选择英文 |

解析规则：

1. 有有效手动选择时优先使用，不由系统或浏览器设置覆盖。
2. `system` 模式按 macOS 的首选应用语言/有序语言列表找到第一个支持项；`zh-*` 映射至简体中文，`en-*` 映射至英文。
3. 其他语言没有支持项时回退至英文；系统语言读取失败也回退至英文。
4. `zh-Hant` 等中文系统也暂显示简体中文，并允许用户手动切英文，不声称提供繁体翻译。
5. 系统语言变化在支持事件中或窗口重新激活时复核；只有 `system` 模式会跟随变化，不保证 OS 权限对话框也能在当前进程即时切换。

macOS 语言来源由原生适配层获取，需在技术验证中确认可读取应用级首选语言及系统回退列表，不能只使用 WebView 的 `navigator.language`。浏览器演示模式可以模拟这个列表，不能用演示结果代替原生验证。

#### 4.6.3 必须翻译的内容

| 表面 | 所有者 | 覆盖范围 |
| --- | --- | --- |
| 主窗口、首次设置、设置、悬浮窗 | React | 标题、字段、按钮、工具提示、单位、空状态和确认框 |
| 菜单栏、应用菜单和窗口标题 | Rust/macOS 适配层 | 打开、设置、隐藏金额、语言、退出与状态摘要 |
| 系统通知 | Rust 提醒服务 | 应用提供的标题和正文；按发送时有效语言构造 |
| 错误、警告、恢复界面 | React/Rust 启动界面 | 错误码对应文案、字段提示、保存失败与文件恢复 |
| 内置鼓励语 | 双语文案资源 | 温和/幽默/休息/收工分类，语义自然而非机械直译 |
| 可访问性 | React/原生层 | 图标按钮的可访问名称、说明和页面 `lang` |
| 安装与帮助 | README、Release 说明 | 两种语言的下载、安装、隐私、更新和已知限制 |

用户昵称、自定义文案和自由输入不自动翻译。已有系统通知不会在通知中心追溯改写，也不会因切换语言重复发送；macOS 自带权限窗口和系统菜单部分内容可能跟随 OS 的语言，而不是应用选择。

#### 4.6.4 资源与代码组织

建议使用成熟的 `i18next + react-i18next`，不手写散落的 `language === "zh" ? ... : ...`。双语资源放在根目录 `resources/locales/`，同时供 React 构建导入和 Rust 编译嵌入。

```text
resources/locales/
├── zh-CN/
│   ├── app.json           # UI、错误、原生菜单和通知
│   └── encouragement.json
└── en-US/
    ├── app.json
    └── encouragement.json
```

- `app.json` 采用稳定的扁平语义 key，例如 `settings.language`；i18next 配置 `keySeparator: false`，Rust 按相同 key 查找，避免两份独立翻译漂移。
- 原生菜单和首版下班通知使用完整固定句资源，不在 Rust 中重新实现 i18next 的复数语法。
- React 的插值和复数由 i18next 处理，禁止拼接句子；昵称等插值内容始终作为普通文本渲染。
- CI 校验普通 key 对齐、插值名一致，复数按语言类别校验：英文通常需要 `_one`/`_other`，中文通常只需要 `_other`，不能粗暴要求所有后缀完全相同。
- 内置鼓励语使用稳定消息 ID，每个 ID 都提供两种语言内容；分类和冷却状态不随语言重置。
- 找不到 key 时回退至内置英文；开发阶段记录缺失 key，发布 CI 拒绝未补齐的必需翻译，不让生产界面显示裸 key。
- 文案不直接写在图片中；无法避免的带字素材要提供双语资源，不能靠缩放图片翻译。

#### 4.6.5 即时切换与多窗口同步

切换是独立的设置操作，不要求保存整个表单，也不重建计薪引擎：

1. 前端提交语言偏好与 `expectedRevision`，Rust 验证允许值。
2. Rust 仅更新语言字段，按安全流程保存 `config.json`；失败则维持旧偏好并提示。
3. 保存成功后更新有效 locale，广播带 revision 和独立 `localeSequence` 的 `locale_changed`，原生菜单更新文字。
4. React 窗口更新 i18next 语言与页面 `lang`，保留输入、焦点、角色状态和计时结果。
5. 未显示的窗口下次打开时读取最新 locale，不能依赖曾经接收到事件。

语言切换应在无待保存表单时通常 500ms 内完成可见更新；保存慢时显示保存中。其他窗口的薪资草稿不自动丢弃：其提交仍需 revision 校验，冲突时保留草稿并提示重新核对。

`localeSequence` 在本次进程中递增，前端按它接受最新语言事件；系统语言变化即使没有改配置 revision，也要生成新序号。`get_locale` 返回同一序号，窗口先订阅再查询，不能仅用配置 revision 丢弃所有“相同 revision”的系统语言更新。启动新进程时重新初始化窗口状态，不沿用上一进程序号。

启动时先解析 locale 再展示首次设置，避免英文/中文闪烁。即使配置损坏，也要能按系统语言显示恢复入口，并提供本次恢复界面的临时语言选择；不能为了切语言覆盖损坏文件。

#### 4.6.6 语言、格式、币种和时区分离

- locale 只决定文案和展示格式，不自动把 `CNY` 改为 `USD`，不换算金额、不改变 21.75 折算参数、不切换到美国时区。
- 建议首版币种菜单先支持 `CNY`、`USD`（范围待确认）；其他币种按需求追加。金额可选 2 或 4 位小数，不宣称实现所有货币的法定小数位规则。
- 配置与 IPC 的金额始终是点号分隔、无千位分组的十进制字符串；日期为 ISO 格式，UTC 时间为 RFC 3339，星期仍采用 ISO 1～7。
- 数字展示对十进制字符串做精确舍入和分组；`Intl.NumberFormat` 可帮助提供 locale 格式信息，但不得通过转换成不精确的 `Number` 重新计算工资。
- 为避免 `$`、`¥` 混淆，完整金额至少在主界面或可访问说明中标明 `CNY`/`USD`；菜单栏紧凑展示也要能查到币种。
- 输入允许半角小数点、不带分组的数字；粘贴可接受经过严格验证的 `1,234.56` 分组，拒绝 `1.234,56` 等未支持的歧义形式，不能误读后静默保存。
- 日期和星期使用 `Intl.DateTimeFormat` 与明确配置时区；班次输入首版统一 24 小时制并显示说明，避免英文界面将 `09:00` 猜为下午。
- 倒计时为时长，不是当地钟表时间；采用 `HH:mm:ss` 或本地化天/小时标签，不能用时区格式器造成回绕。
- 英文布局允许换行，关键金额与按钮不能被裁掉；系统字体使用支持中文和英文的回退栈，图标不使用国旗代表语言。

#### 4.6.7 文案示例与边界

| key | 简体中文 | English |
| --- | --- | --- |
| `app.title` | 上班鼓励器 | Salary Pulse |
| `dashboard.todayEstimate` | 今日估算 | Today's Estimate |
| `dashboard.clockOutIn` | 距离下班 | Time Until Clock-Out |
| `status.working` | 工作中 | Working |
| `status.finished` | 已收工 | Done for Today |
| `common.settings` | 设置 | Settings |

| `notification.clockOutTitle` | 到下班时间了 | It's Time to Clock Out |

英文“Estimated Earnings”不能写成“Paid”或“Money Received”，中文也不使用“已到账”，避免把估算翻译成真实付款。英文幽默文案由人工校对，保持轻松但不生硬直译“牛马”。

## 5. 技术选型与决策

### 5.1 桌面方案对比

| 方案 | 优点 | 代价与风险 | 对本项目的判断 |
| --- | --- | --- | --- |
| Tauri 2 + React | 使用系统 WebView，通常包体较小；适合 TypeScript 界面；支持桌面插件 | 需要 Rust；macOS 原生边界可能需要桥接；WebView 兼容性要测 | 默认推荐 |
| Electron + React | JavaScript 生态成熟；与已读参考项目技术栈接近；桌面能力丰富 | 自带 Chromium，通常包体和常驻资源开销较大 | 团队只熟悉 JS 或要较快改造现有 Electron 项目时合理 |
| SwiftUI + AppKit | macOS 集成直接；菜单栏、能耗和系统行为可精细控制 | 需要 Swift；仅面向 Apple 平台；部分 UI 仍要 AppKit | 明确永远只做 Mac，且熟悉 Swift 时值得优先考虑 |
| 网页 / PWA | 原型快、部署容易 | 难提供一致的菜单栏、原生置顶和完整退出语义 | 可用作界面预览，不作为正式桌面交付 |
| Python GUI | 快速验证计算逻辑 | 视觉体验、分发体积、原生集成通常需更多工作 | 不作为当前默认方案 |

推荐 Tauri 并不是认定它在任何情况下都优于 Electron。这里的决定基于“长期常驻、Mac 本地、界面可用 Web 技术、未来可能跨平台”。若开发者只熟悉 JS，减少学习成本可能比包体更重要。

### 5.2 推荐技术栈

| 层次 | 技术 | 具体用途 |
| --- | --- | --- |
| 桌面运行时 | Tauri 2 | `.app`、窗口、菜单、系统托盘和 IPC |
| 前端 | React + TypeScript | 视图、表单、主题、互动状态 |
| 前端构建 | Vite | 本地开发、静态资源打包 |
| UI 状态 | Zustand | 最新快照、界面偏好、互动状态；不持有工资账本 |
| 表单校验 | Zod | 前端输入检查；Rust 仍重复校验所有写入 |
| 图标 | lucide-react | 工具按钮、状态和菜单图标 |
| 本地化 | i18next + react-i18next；共享内置 JSON 资源 | 中文/英文切换、插值和复数、React 与原生文本一致 |
| 领域后端 | Rust | 计薪、排班、时钟、持久化和系统调用 |
| 时间处理 | chrono + chrono-tz | 带时区排班、跨日、夏令时解析 |
| 十进制 | rust_decimal | 薪资与费率的精确计算 |
| 持久化 | 本地 JSON 文件 + Rust 文件 API | 用户配置、少量恢复状态、安全替换写入 |
| 序列化 | serde / serde_json | 配置文件与 IPC 的结构化解析和校验 |
| 原生插件 | 官方 autostart、notification、single-instance | 自启、通知、单实例 |
| 前端测试 | Vitest + Testing Library | 组件、状态转换、桥接契约 |
| UI 自动测试 | Playwright（浏览器预览） | 布局、可访问性、用户流程；不冒充 Mac 原生测试 |
| Rust 测试 | cargo test；可选 proptest | 金额、区间、迁移、性质测试 |
| 质量工具 | ESLint、Prettier、rustfmt、Clippy | 静态检查和统一格式 |
| 包管理 | npm + package-lock.json；Cargo.lock | 锁定依赖版本 |
| CI | GitHub Actions | 测试、双架构构建、发布草稿 |

不在此固定 React/Vite 等生态包的具体小版本。初始化时选取互相兼容的稳定版本，确认 Node.js、Rust、Tauri 和插件要求，再提交锁文件。Tauri 的 crate、CLI 和插件必须使用兼容的版本系列。

### 5.3 关键架构决策

| 决策 | 原因 | 被排除或暂缓的方案 |
| --- | --- | --- |
| Rust 是唯一计薪权威 | 多窗口和休眠后结果一致，避免 JS/Rust 两套算法 | React 自己逐秒加金额 |
| 排班驱动，不按应用在线时长 | 用户合盖或退出不应该丢失计划内估算 | 把程序运行时长当作考勤 |
| 本地配置文件是设置唯一来源 | 个人小工具数据量小，可查看、备份，不需要数据库 | SQLite、远程数据库、多个 WebView 各存一份配置 |
| 开机自启、提醒默认关闭 | 尊重用户，降低打扰与权限负担 | 首次启动直接常驻和请求全部权限 |
| 原创 2D 角色 | 降低资源、复杂度和版权风险 | 首版 3D 场景和复杂物理 |
| 首版手动下载更新 | 保持离线和发布链路简单 | 一开始就加入强制自动更新 |
| 不自建服务端 | 当前核心功能不依赖网络 | 账号、云数据库和远程配置 |
| 单应用双语，语言与计薪隔离 | 不重复构建语言版，不混用币种或时区 | 中文/英文两套工程、在线语言包 |

## 6. 系统架构与运行流程

### 6.1 分层架构

```text
React 界面层
  主窗口 / 设置 / 菜单栏面板 / 悬浮窗 / 角色状态
                  │ 类型化命令与事件（Tauri IPC）
                  ▼
Rust 应用服务层
  单一串行命令队列 / 设置服务 / 快照服务 / 提醒服务 / Locale 服务
                  │
        ┌─────────┼──────────────────┐
        ▼         ▼                  ▼
Rust 领域层      本地持久化层          macOS 适配层
工资估算         config.json          菜单栏 / 窗口
排班解析         state.json           通知 / 开机自启
日期例外         安全文件写入          电源与屏幕事件
时钟抽象         格式升级与备份        原生能力可行性验证
        ▲
        │ 每秒时钟信号 + 唤醒/配置变化/日期变化时立即重算
        └──────── 最新快照同时供给所有界面和菜单栏
```

关键关系：定时器只通知“现在需要重新计算”，不是金额累加器。实时金额保存在内存中，不每秒写入文件。

### 6.2 状态所有权

| 状态 | 所有者 | 是否持久化 |
| --- | --- | --- |
| 薪资、排班、例外、生效时间 | Rust 设置服务 + config.json | 是 |
| 当前收入和倒计时快照 | Rust 快照服务 | 否，可从规则和时间重算 |
| 通知已发送记录 | Rust 提醒服务 + state.json | 是，限制保留数量 |
| 当前页面、表单草稿 | React | 否 |
| 角色短暂动作 | React 互动状态机 | 通常否 |
| 主题、隐私模式、窗口位置 | config.json，Rust 对外提供 | 是 |
| 登录项是否有效 | macOS 系统 | 不以 UI 缓存值代替真实结果 |
| 语言偏好 | Rust Locale 服务 + config.json | 是，`system` / `zh-CN` / `en-US` |
| 当前有效 locale | Rust 解析后广播，各窗口 i18next 使用 | 否，从偏好和系统语言重算 |

### 6.3 启动流程

1. 单实例插件判断是否已有进程；存在则唤起已有实例并退出新实例。
2. 确认本应用用户数据目录和可写性，不写入 `.app` 或 DMG。
3. 首次运行创建默认配置；已有配置则解析 JSON，检查格式版本并按需升级。
4. 加载设置和业务规则，检验有效性；在创建界面/原生菜单前解析语言，损坏配置的恢复界面也有语言回退。
5. 创建菜单栏入口，避免首次配置前就暴露示例金额。
6. 没有有效配置则打开设置；否则生成当前快照。
7. 根据用户偏好决定主窗口和悬浮窗是否显示。
8. 启动 Rust 时钟任务，注册必要系统事件。
9. 不主动要求通知授权；授权从用户启用提醒时触发。

配置文件已存在但无法读取或解析时，程序进入恢复界面，不静默覆盖用户配置。首次运行且文件不存在才创建默认配置。

### 6.4 每次重新计算

1. 从 `Clock` 取得当前 UTC 时间，并按已配置时区解析工作日期。
2. 找到当前、上一和下一锚定日期的班次，识别跨午夜场景。
3. 选择已冻结的班次规则版本，生成有薪区间并裁剪到当前时间。
4. 计算本班次金额、今日金额、工作进度、状态与剩余秒数。
5. 分配递增快照序号，更新内存中的权威快照。
6. 向已打开的窗口广播事件；原生菜单栏使用同一快照更新。
7. 如跨越提醒触发点，检查静默规则和持久化去重记录。

### 6.5 配置修改流程

1. 前端先校验格式，提交 `expectedRevision` 与修改内容。
2. Rust 再验证金额、排班和冲突，拒绝非法写入。
3. 构造完整的新配置，包括下一班次生效的待应用规则；安全写入临时文件并替换 `config.json`。
4. 文件保存成功后更新内存规则；失败则保留旧规则。
5. 广播配置变更和最新快照；前端收到确认后才显示“已保存”。

P0 中薪资和计薪排班修改默认下一个尚未开始的班次生效；主题、金额隐藏等界面设置立即生效。已开始班次冻结所用版本，避免改薪后今日数字突然变成另一种口径。

语言属于立即生效设置，单独 patch 保存，不能跟随待生效薪资规则延迟到下一班次；语言变更不改变班次规则编号或计薪费率。

## 7. 工资估算与时间规则

这是项目最重要的业务定义。动画可以晚些完善，计薪规则必须先写清楚并测试。

### 7.1 名词与默认值

| 名词 | 定义 |
| --- | --- |
| 班次 | 从上班到下班的一个计划区间，允许跨午夜 |
| 锚定日期 | 班次开始时间在配置时区中的日期 |
| 有薪区间 | 班次中用于估算金额的时间段；无薪休息不包含在内 |
| 今日估算 | 属于当前本地自然日 `[00:00, 次日00:00)` 的有薪时间估算 |
| 本班次估算 | 当前跨日或非跨日完整班次截至现在的估算 |
| 折算工作日数 | 月薪转换成每工作日估算的用户参数；默认 21.75，可修改 |
| 标准每日有薪工时 | 费率折算的固定分母，默认 8 小时，与实际每班时长分开定义 |
| 生效起点 | 用户选择开始估算的 UTC 时间，早于此时间的金额不生成 |

21.75 只是常见的月薪折算展示参数，不代表该用户的法定工资计算方式，也不代表每个月真实排班天数。界面应显示所用参数，并说明估算不是实际工资结算。

### 7.2 薪资模式

P0 支持月薪和时薪；P1 增加年薪和周薪。

设：

- `S`：所选周期薪资金额。
- `D`：该周期折算工作日数。
- `H`：标准每日有薪工时。
- `R`：每秒估算收入。

公式：

```text
月薪模式：R = 月薪 / (月折算工作日数 × 标准每日有薪工时 × 3600)
时薪模式：R = 时薪 / 3600

P1 年薪模式：R = 年薪 / (年折算工作日数 × 标准每日有薪工时 × 3600)
P1 周薪模式：R = 周薪 / (周折算工作日数 × 标准每日有薪工时 × 3600)
```

年薪和周薪直接使用各自用户设定的分母，不偷偷假定一年总是 365 天、不把周薪随意乘 52 后套用另一种分母。闰年只影响日历，不影响用户明确设定的固定折算参数。

### 7.3 示例：月薪 10,000 元

配置：

- 月薪 `10000.00 CNY`。
- 月折算工作日 `21.75`。
- 标准每日有薪工时 `8`。
- 上班 `09:00`，下班 `18:00`。
- 午休 `12:00～13:00`，无薪。

```text
每工作日估算 = 10000 / 21.75 ≈ 459.77011494 元
每小时估算   = 10000 / (21.75 × 8) ≈ 57.47126437 元
每秒估算     = 10000 / (21.75 × 8 × 3600) ≈ 0.01596424 元
```

| 时间 | 已计薪时长 | 显示金额（2 位小数） | 状态 |
| --- | --- | --- | --- |
| 08:59 | 0 小时 | 0.00 | 未上班 |
| 10:00 | 1 小时 | 57.47 | 工作中 |
| 12:00 | 3 小时 | 172.41 | 午休开始 |
| 12:30 | 3 小时 | 172.41 | 无薪午休 |
| 13:00 | 3 小时 | 172.41 | 恢复工作 |
| 18:00 | 8 小时 | 459.77 | 已下班 |
| 20:00 | 8 小时 | 459.77 | 已下班，不自行算加班 |

如果把午休改为有薪，而其他参数不变，则当天计薪 9 小时，金额约为 `517.24`，不会仍然强行显示 `459.77`。设置页应预览这一结果，并解释“标准有薪工时”与“实际有薪班次时长”的区别。

如果每天工作时间不同，较长班次在固定时薪等价口径下会产生较高估算。这不表示固定月薪在现实中一定按每天工时浮动。

同样，如果当月实际有薪工作日数不是 21.75，按上述固定费率加总的“本月估算”不一定等于 10,000 元；不应在月末自动把差额补成月薪。若以后需要“当月工资预算严格分摊到实际排班”的另一种口径，应新增独立模式，冻结当月分母，并测试排班变更，不暗中改变本模式。

### 7.4 时间区间算法

所有时间区间使用半开区间 `[start, end)`，避免边界秒重复计入。

```text
计划班次 S = [start, end)
无薪休息集合 U = 合并后的无薪休息区间
有薪区间集合 P = S - U
有效区间 = P 与 [规则生效起点, now) 的交集
有效计薪秒数 = 所有有效区间长度之和
估算金额 = Σ(区间秒数 × 该区间所属规则的每秒费率)
```

区间算法必须由领域层统一实现，覆盖相邻区间、重叠休息、跨日和异常输入。合法休息需处于班次内；P0 对重叠休息直接拒绝输入，领域层仍防御性合并，避免重复扣减。

### 7.5 下班倒计时与进度

```text
距下班秒数 = max(0, 班次结束时间 - now)
班次进度 = 已经过的班次墙钟秒数 / 班次总墙钟秒数
有薪进度 = 已计薪秒数 / 本班次计划有薪秒数
```

- 主界面标明“班次进度”还是“计薪进度”，不混用。
- 午休时距下班秒数继续减少；无薪休息时金额不增长。
- 上班前显示“距上班”；下班后显示“已收工”及下一班次摘要。
- 没有工作班次的日期显示“休息日”，不从当前时间开始额外计薪。
- 时长格式在超过 24 小时时用“天 + 小时”，不使用会按 24 小时回绕的时间格式化方式。

### 7.6 工资状态与角色状态分开

工资状态：

```text
UNCONFIGURED → OFF_DAY / BEFORE_SHIFT / WORKING / PAID_BREAK /
               UNPAID_BREAK / AFTER_SHIFT / ERROR
```

角色状态：

```text
IDLE / WORKING / RESTING / CHEERING / FINISHED
P1：LISTENING / PHONE / TOILET / REWARD
```

“互动加速”“得到奖励”只影响视觉反馈和趣味积分，不改变费率。P1 若加入带薪如厕动作，默认仍按班次有薪区间计算，不声称记录了真实休息时长。

### 7.7 跨午夜与自然日统计

例如班次为 `22:00～次日06:00`：

- 班次 ID 使用开始日期，不能在午夜自动新建另一个相同班次。
- 本班次金额一直计算到次日 06:00。
- 今日金额按午夜拆分：第一天统计 22:00～24:00，第二天统计 00:00～06:00。
- 工作日和休息日判断使用锚定日期；前一天开始的夜班不会因次日是周末而被腰斩。
- P0 每个锚定日最多一个班次，班次长度必须大于 0 且小于 24 小时；相邻日期班次不能重叠。
- 跨日休息配置使用相对于班次起点的分钟偏移，或显式 `dayOffset`，不能只用裸 `HH:mm` 猜测是哪一天。

### 7.8 节假日、调休与加班

- P0 使用用户可编辑的日期例外：休息日、额外工作日、替换班次。
- 例外优先于周排班；已开始班次所用规则不随意重写。
- 不把“周六周日”当作所有用户的休息日，也不把中国调休政策写死进代码。
- P1 若提供节假日数据，随包携带来源、年份和版本；无数据时提示并允许用户确认，不伪称已联网获取。
- P0 下班后停止计薪，没有加班工资倍率；用户可以提前把当天设置为较长班次，仍按同一估算费率。
- P1 如支持实际加班，必须新增明示的加班区间和自定义费率，不将其解释为法定倍率。
- 休息日显示零“计划工作时间估算”，不代表固定月薪用户在现实中这一天没有工资。

### 7.9 首次使用与修改生效时间

- 默认从“完成设置的当前时间”开始估算，不自动生成过去数月的收入。
- 首次设置可以选择“从今天本班次上班时开始”，需要明确预览和确认。
- 保存准确的 `trackingStartedAtUtc`，并在所有区间计算中裁剪。
- P0 改薪、改折算参数、改排班默认下一班次生效，当前班次保留旧版本。
- `config.json` 保存当前规则和一份待生效规则；已开始班次只保留少量完整规则快照，不建立无限增长的薪资版本库。
- 首版不保存多年历史工资账本。后续若增加统计，必须另行定义历史快照，不用当前薪资冒充过去收入。
- 历史更正、立即切换、已开始班次修改和删除规则属于 P1，需要确认、审计来源和统计重算测试。

待生效规则的边界必须在保存时计算并显示具体日期：已开始班次按旧规则完成，新规则从其结束后、按**新排班**找到的第一个未开始班次生效；没有当前班次时只找开始时间不早于保存时刻的新班次，不回填已过去的当日时段。未来 366 天内没有符合条件班次时保留原规则并提示调整，不保存无法执行的生效计划。尚未生效时再次修改，替换该份待生效规则并重新预览日期，不排队创建多个版本。跨午夜、币种变化与日期例外必须一起检查，不能仅取 `now + 24h`。

### 7.10 休眠、合盖、退出与时钟变化

本产品采用“按排班时间估算”，不是“应用运行时长计费”。因此：

- 合盖休眠期间如果处于计划有薪区间，唤醒后金额会补齐，这是预期行为。
- 应用退出后不运行计时器、不发通知；再次启动按规则重算这段期间的估算。
- 只在应用打开时显示动画和发送提醒，不能宣称退出后仍能提醒。
- 不依赖 `setInterval` 调用次数。隐藏窗口和休眠会暂停浏览器定时器，但不能影响结果。
- UTC 墙钟用于排班判断，单调时钟用于动画和检测墙钟突变。
- 系统时间被调回时，按修正后的墙钟重算，金额允许下降并提示“系统时间发生变化”；不为了单调增长伪造金额。
- 多窗口序号只用于防止旧快照覆盖新快照，不强制金额单调。

### 7.11 时区与夏令时

- 初始时区读取系统设置，明确存为 IANA 时区，如 `Asia/Shanghai`。
- P0 时区固定为用户选定值，系统时区变化后提示用户确认，不静默改变排班含义。
- 计划班次先按当地日期和当地时刻构造，再转换成 UTC 计算真实秒数。
- 对夏令时回拨产生的重复时刻：开始采用较早实例、结束采用较晚实例，并在受影响班次上提示。
- 对夏令时跳过产生的不存在时刻：不猜测，标记该班次无效并要求日期例外修正。
- Asia/Shanghai 当前不涉及夏令时，但仍需测试这些规则，避免用户切换时区后产生隐蔽错误。

### 7.12 数字精度与显示

- 输入薪资作为十进制字符串传输，例如 `"10000.00"`。
- Rust 使用 `rust_decimal`，不使用二进制浮点数累计金额。
- JSON 配置中的薪资和折算参数保存为十进制字符串；实时金额不逐秒持久化。
- IPC 中金额也是字符串；TypeScript 不对金额 `parseFloat` 后再计算。
- 前端通过十进制安全格式化器添加分组和币种，不依靠浮点数转换保证精确。
- 内部保留足够小数，最终展示采用 `MidpointAwayFromZero`（正金额的 half-up 四舍五入）；2 位或 4 位小数仅是展示选项。React 和原生菜单使用相同十进制舍入测试样本，不能分别默认采用不同规则。
- 收入累计不在每秒舍入，最终展示才舍入，避免低时薪误差不断累积。
- 首版币种随规则保存，建议初始菜单支持 CNY/USD（币种范围尚待确认），不做汇率换算；更换币种需要重新确认薪资金额，不是给旧金额换一个符号。
- 不允许同一“今日估算”将 CNY 和 USD 相加。币种修改的生效点要选择一个不存在旧币种有薪区间的后续自然日班次，并预览日期；跨午夜旧班次必须结束且避开它占用的自然日。P0 不提供混合币种总数，无法确认时拒绝更改，而不是套用新符号。
- 业务输入设置合理上限，例如薪资最大 `1,000,000,000.00`、每日标准工时 `(0,24]`，并验证乘除不会越界。

### 8.2 排班与计薪核心应为纯函数

领域函数接收显式参数，返回结果或可解释错误。测试中传入固定 `now`，不修改系统时间。

```text
resolveShift(anchorDate, scheduleVersion, exceptions, timezone)
resolvePaidIntervals(shift, breaks)
estimateAmount(intervals, salaryVersion, cutoff, trackingStart)
buildSnapshot(now, resolvedRules)
```

Rust 领域层不引入 Tauri 窗口类型，方便单独测试，未来换桌面框架时仍能复用核心逻辑。

### 8.3 鼓励语设计

按温和、幽默、下班、休息、目标达成等类别组织，记录最近出现的若干条 ID，避免连续重复。

- 默认轮换间隔约 10～20 分钟，只更新界面，不每次发系统通知。
- 昵称插入使用普通文本渲染，不使用 `dangerouslySetInnerHTML`。
- 可以关闭所有鼓励语，避免打扰。
- 不默认使用羞辱、PUA、健康诊断或强迫加班文案。
- 自定义文案导入属于 P1，只允许结构化文本，不执行脚本。
- 首版不需要大模型 API，降低成本和隐私风险。
- 每条内置消息都有稳定 ID 和中英文内容；切换语言使用同一 ID 对应内容，不清空冷却或重置随机轮换。

### 8.4 通知的可靠性边界

- 默认不开启；用户点击启用下班提醒时才申请授权。
- 触发窗口：从下班时刻起最多 5 分钟；唤醒后超过该窗口不补发过期通知。
- 下班前提醒若在 P1 增加，使用独立事件 ID 和更短补发窗口。
- 事件 ID 包含规则版本、班次锚定日期和提醒类型，避免午夜、重启或多窗口重复。
- 应用提交通知不等于用户实际看见；系统专注模式可能延迟或隐藏。
- 首版选择“至多一次尝试”：先持久化领取事件，再向 OS 提交；若崩溃发生在两步之间，可能漏发。
- OS 返回明确错误时显示可诊断状态，不无限重试。状态文件写入与系统通知不是一个原子操作，不能宣称“严格恰好一次”；去重状态保存失败时不发送通知。

静默时段定义为配置时区的每日半开区间 `[start, end)`，开始大于结束时跨午夜，例如 `22:00～07:00`；相等时不允许启用，避免“全天”或“零时长”的歧义。命中静默时段或提醒已关闭的事件直接标记为已抑制，不在解除静默、切换语言或随后开启提醒时补发；系统专注模式仍由 macOS 管理。

通知事件 ID 使用班次锚定日期、稳定业务规则 ID 和提醒类型，不使用通用设置 revision、locale 或翻译文本。否则改主题或切语言就可能重新生成 ID，导致重复通知。正文在实际发送前按当前 locale 构造。

## 9. 数据模型与本地存储

### 9.1 存储位置

应用安装包只包含程序与默认资源。首次运行时使用 Tauri 应用数据目录 API，在当前用户本机创建文件，通常位于：

```text
~/Library/Application Support/<固定应用标识>/
├── config.json                 # 薪资、排班、个人偏好
├── state.json                  # 少量班次恢复信息和提醒去重
├── config.json.bak             # 最近一份有效配置备份
├── state.json.bak              # 最近一份有效恢复状态
└── logs/                       # 不含薪资的诊断日志，可选
```

这里的路径是说明性示意；实际路径由 Tauri 和应用标识确定，不把用户主目录写死在源码中。应用标识建议形如 `com.<维护者>.salarypulse`，在首次正式发布前确定，之后保持不变。

- 不部署数据库，不打包 SQLite，不要求用户安装任何数据服务。
- 薪资不放在项目仓库、DMG、`.app` 或 `.env` 中，每个 macOS 用户账号使用自己的数据目录。
- 多窗口都通过同一个 Rust 设置服务读写，避免同时覆盖文件；前端不另存一份 localStorage 配置。
- `schemaVersion` 表示文件格式版本，`revision` 是防止旧表单覆盖新设置的简单递增编号，不是数据库概念。
- 设置页提供“打开本地数据目录”；用户可以备份文件，无需在 Finder 中寻找隐藏路径。

### 9.2 配置与状态的分工

| 文件 | 保存内容 | 更新时机 |
| --- | --- | --- |
| `config.json` | 语言偏好、昵称、薪资、周排班、日期例外、主题、隐私、通知偏好、窗口位置、待生效规则 | 用户保存设置；窗口位置变化使用去抖 |
| `state.json` | 开始估算时间、少量已开始班次的规则快照、最近通知事件 ID | 首次开始、班次切换、发送提醒前 |
| `config.json.bak` | 最近一份已验证且完整的配置 | 成功替换新配置前更新 |
| `state.json.bak` | 最近一份已验证状态，含恢复所需班次规则快照 | 安全替换状态文件前更新 |
| `history.json`（P1，按需） | 有界的日汇总，例如最近 12 个月 | 日结或用户主动生成；不是首版依赖 |

实时金额与倒计时由配置、时间和必要班次快照重算，不每秒存盘。角色短暂动作不需要持久化。

为了保留“修改薪资从下一班次生效”的体验，`config.json` 可以增加一个 `pendingRules` 对象，包含待生效薪资、排班和生效时间。它只是少量结构化配置，不建立多张数据表或完整版本历史。

`state.json` 中只保存最近约 7 天的已开始班次完整规则快照，用于跨午夜和重启后的当前日展示；未来班次预览不能提前冻结。待生效规则启用前先持久化仍需要的旧班次快照，写入失败则不移除旧规则；两份文件的提交不是整体原子操作，恢复时按班次 ID 幂等处理并验证规则编号，不能假设它们一定同步写成。

首版不展示超出保留范围的历史统计。应用退出期间没有变更规则时，当前班次仍可根据已保存配置重建；不是因为缺少运行记录就不计薪。若恢复所需规则无法确认，显示可恢复错误，而不是静默套用新薪资。

**最小完整契约：**

- `config.json` 顶层包含 `schemaVersion`、`revision`、独立 `rulesId`、当前规则，以及可空的 `pendingRules`（新规则 ID、完整薪资/排班和 `effectiveFromUtc`）。`revision` 用于所有设置保存冲突，`rulesId` 只在计薪规则变化时改变，语言/主题不改变它。
- `state.json` 顶层包含自己的 `schemaVersion`、`trackingStartedAtUtc`、有界的 `shiftSnapshots` 和 `notificationReceipts`；班次快照包含班次 ID、规则 ID、完整费率参数、币种、时区、已解析 UTC 区间。不能只存一个找不到来源的版本 ID。
- 启用待生效规则的顺序固定：先保存所有仍需展示的旧班次完整快照到 `state.json`，成功后再安全替换 `config.json` 并清除 `pendingRules`。崩溃后若旧配置仍存在，按相同 ID 重做；若新配置已存在，使用已保存快照，不重复累计金额。
- 从 `.bak` 恢复不能只检查 JSON 可解析。必须校验当前日/跨日班次与待生效规则是否仍可完整解析；只有有效配置与状态的组合通过校验才进入正常模式。较新班次快照不能被较旧备份配置重算覆盖。
- 首次安装可创建缺失状态文件；已有配置却丢失 `state.json` 时不能自动把 `trackingStartedAtUtc` 重置为现在。先尝试有效备份，无法恢复则让用户明确选择重新开始，避免悄悄丢失当前日估算。
- P0 不承诺在手动编辑规则文件后保留旧班次账本；检测外部修改时阻止覆盖并提供校验、恢复入口，不将未知状态当作有效历史。

建议输入和文件上限：配置 1 MiB、状态 1 MiB、昵称 40 个 Unicode 字素、日期例外 366 条、每班休息 8 条、保留通知记录最多 256 条且不早于最近 7 天。达到上限时按明确规则清理过期状态或拒绝新增；读取前校验文件大小，禁止无限数组或过深嵌套拖垮常驻进程。具体数值初始化时可调整，但必须有测试和用户可理解的错误。

### 9.4 数据恢复与迁移

**安全保存流程：**

1. 用结构化解析和 Rust 校验生成完整新配置，不拼接 JSON 字符串。
2. 由单一写入队列处理；保存前检查 revision，并检测磁盘文件是否被外部修改。
3. 在同一目录创建唯一临时文件，限制文件权限，写入完整内容并 `sync_all`。
4. 保留最近一份已验证配置备份；备份失败时不继续覆盖原配置。
5. 在同一文件系统上通过 rename 替换目标文件，避免直接截断原文件；按平台能力同步目录。
6. 保存成功才更新内存和提示；失败保留旧文件，并安全清理本次临时文件。

这能降低中断导致半份 JSON 的风险，但不宣称能抵御所有磁盘故障。配置和备份默认仅当前用户可读写，目录权限尽可能限制为当前用户。

**升级和恢复：**

- 文件格式升级先在内存转换并验证，成功后按安全保存流程落盘，保留升级前备份。
- 检测到比当前程序更新的文件格式时拒绝写入，避免降级覆盖。
- 文件损坏时提示从有效 `.bak` 恢复或重新设置；未经确认不删除、不重置。
- 不支持在程序运行时随意热加载手工修改；外部文件有变化则提示重新加载，并检查待生效和班次快照一致性。
- 备份也含私人薪资，不默认提交到 GitHub Issue。
- “删除个人数据”明确确认范围：本应用配置、状态、备份和私人缓存；不删除用户自行导出的文件。
- 删除 `.app` 不等于删除配置；更新安装包默认保留用户数据。

### 9.5 P1 导出与导入

- 导出默认排除薪资和班次快照，包含私人薪资需要单独勾选和风险说明；直接备份本地文件则可能包含薪资。
- 文件带 `formatVersion`、导出时间和类型；设置大小与条数上限。
- 用结构化解析器验证字段、金额、时间、版本和资源引用。
- 导入前预览差异并备份；确认后安全替换配置文件，不进行部分字段的逐项落盘。
- 不执行导入文件中的 HTML、JavaScript、shell 或任意 URL。
- 加密备份若采用密码派生和认证加密，应使用成熟库，另行设计密码丢失和密钥管理。

## 10. 前后端通信契约

### 10.1 命令与事件

| 类型 | 名称 | 输入或输出 | 说明 |
| --- | --- | --- | --- |
| 命令 | `get_settings` | 返回配置和 revision | 初始化设置页 |
| 命令 | `save_settings` | patch、expectedRevision、生效策略 | 原子保存，返回新 revision |
| 命令 | `get_locale` | 返回偏好、effectiveLocale、revision、localeSequence | 窗口启动与重开同步 |
| 命令 | `set_language` | language、expectedRevision | 只保存语言，返回有效 locale、新 revision 和 localeSequence |
| 命令 | `get_snapshot` | 返回当前快照 | 打开窗口或丢失事件后同步 |
| 命令 | `set_salary_privacy` | boolean | 所有窗口同步，不只修改当前窗口 |
| 命令 | `set_floating_visible` | boolean | 创建、显示或隐藏悬浮窗 |
| 命令 | `request_notification_permission` | 返回权限状态 | 只从用户主动操作调用 |
| 命令 | `set_launch_at_login` | boolean | 调用 OS，返回实际结果 |
| 命令 | `reset_user_data` | 确认令牌 | 删除明确范围的个人数据 |
| 事件 | `snapshot_updated` | `WorkdaySnapshot` | 统一快照 |
| 事件 | `settings_changed` | revision、变更类别 | 多窗口协调 |
| 事件 | `locale_changed` | preference、effectiveLocale、revision、localeSequence | 按独立 localeSequence 排序，系统语言改变不必改配置 revision |
| 事件 | `system_state_changed` | 唤醒、时钟跳变、显示器变化 | 触发界面同步和提示 |
| 事件 | `recoverable_error` | 错误码、可恢复建议 | 不暴露内部路径和薪资 |

窗口拖动和常规显示优先使用 Tauri 官方窗口 API，并在 capabilities 中严格限制；不为所有操作自造宽泛的 `execute_action` 命令。

### 10.2 快照类型示意

```ts
type WorkStatus =
  | "UNCONFIGURED"
  | "OFF_DAY"
  | "BEFORE_SHIFT"
  | "WORKING"
  | "PAID_BREAK"
  | "UNPAID_BREAK"
  | "AFTER_SHIFT"
  | "ERROR";

interface WorkdaySnapshot {
  sequence: number;
  generatedAtUtc: string;
  localDate: string;
  timezone: string;
  shiftId: string | null;
  shiftAnchorDate: string | null;
  rulesId: string | null;
  status: WorkStatus;
  currency: string;
  estimatedTodayAmount: string | null;
  estimatedShiftAmount: string | null;
  paidSeconds: number;
  secondsUntilClockOut: number | null;
  secondsUntilNextShift: number | null;
  shiftProgress: number | null;
  salaryHidden: boolean;
  warnings: Array<{ code: string; params?: Record<string, string> }>;
}
```

- 隐私模式时发给展示窗口的金额字段可以置 `null`，权威服务保留内部值。
- 错误状态金额也可为 `null`，不把错误伪装成 `0.00`。
- `shiftProgress` 为无货币意义的比例，可以使用浮点数。
- `sequence` 由单实例 Rust 服务递增，前端丢弃较旧快照。
- Rust DTO 与 TS 类型通过生成或契约测试保持一致，禁止字段命名漂移。
- 状态、错误、警告和班次规则都传稳定机器码与参数，不传已翻译长句；各窗口按 locale 渲染，日志保留机器码。

### 10.3 事件订阅竞态

窗口初始化先安装事件监听，再调用 `get_snapshot`；使用序号比较事件和查询结果。卸载组件时清理监听，防止打开关闭窗口后出现多次回调。

Vite 浏览器开发模式没有 Tauri 环境时，使用 `DesktopBridge` 的演示实现提供固定测试快照，不在浏览器另写一套计薪引擎。演示页明显标记“演示数据”，不能被当成已经实现的原生程序。

### 10.4 错误模型

统一错误码，例如：

```text
VALIDATION_ERROR
REVISION_CONFLICT
INVALID_SHIFT
AMBIGUOUS_TIME_WARNING
NONEXISTENT_LOCAL_TIME
STORAGE_UNAVAILABLE
MIGRATION_FAILED
PERMISSION_DENIED
UNSUPPORTED_PLATFORM
```

前端把错误转换成用户能理解的文案，开发日志记录错误类别和上下文，不默认打印全部请求载荷。

错误结构建议为 `{ code, field?, params?, retryable }`，不得把原始文件内容作为参数传给 UI 或日志。配置读取失败时的原生恢复路径也必须具备内置中英文错误文案。

## 11. macOS 集成与兼容性

### 11.1 菜单栏

- 使用 Tauri 系统托盘能力和适合深浅菜单栏的 template icon。
- 可显示图标、简短倒计时或隐藏金额摘要，支持较窄菜单栏和刘海屏。
- 菜单项至少包含打开主窗口、设置、显示/隐藏悬浮窗、隐藏金额和退出。
- 面板依据图标位置和显示器可用区定位；坐标的逻辑像素与物理像素转换必须测试。
- 如果 Tauri 普通窗口无法满足不激活的原生 popover 体验，首版可先用普通紧凑窗口；是否加入 AppKit 桥接由技术验证决定。
- 不依赖私有 API，也不承诺普通置顶窗口一定覆盖所有全屏应用和 Spaces。

### 11.2 悬浮窗

- 独立窗口标签，缩小 IPC 权限；不挂载整个设置页。
- 使用官方拖动区域或窗口 API，拖动区域不包含可点击按钮。
- 初始不强制抢焦点；用户点击时可交互。
- 位置以显示器标识、逻辑坐标和缩放信息保存，断开外接屏后钳制到当前可用区域。
- 菜单栏提供“重置悬浮窗位置”，避免窗口被保存到屏幕外。
- 置顶是用户选项；点穿属于 P1，启用后必须有菜单栏恢复入口。
- 要在普通桌面、全屏、Mission Control、多屏和 Stage Manager 上验证行为差异。

### 11.3 生命周期与电源事件

- 关闭窗口、最小化、隐藏、锁屏、休眠和退出是不同事件。
- Rust 计薪不依赖 WebView 可见性。
- 系统唤醒后立即重算；没有稳定原生事件支持时以当前快照请求和周期重算作为可靠性兜底。
- 唤醒、时区/时钟变化和显示器事件不应臆造 Tauri API；先做小型验证，必要时使用维护良好的 crate 或 AppKit/系统通知桥接。
- 桥接代码留在 `platform/macos/`，通过 `cfg(target_os = "macos")` 隔离。

### 11.4 开机自启

- 使用兼容版本的官方 autostart 插件，验证其在目标 macOS 上的实际行为。
- 用户主动打开后才注册；失败回滚 UI，并提供系统设置入口说明。
- 系统可能显示后台项目或登录项通知，这不等于程序出错。
- 应用在临时目录运行时，不建议直接启用登录项；提示先移动到“应用程序”。
- 卸载前可在应用中关闭登录项，清理范围只限本应用注册内容。

### 11.5 权限边界

P0 原则上只可能需要用户主动启用后的系统通知权限；开机自启另受登录项机制管理。

不需要屏幕录制、摄像头、麦克风、通讯录、完全磁盘访问或输入监控。P1 的全局快捷键若加入，需要单独验证系统行为；不能提前承诺所有系统版本都不需要任何额外授权。

### 11.6 CPU 架构与系统版本

- Apple Silicon：`aarch64-apple-darwin`，用于 M 系列 Mac。
- Intel：`x86_64-apple-darwin`，用于 Intel Mac。
- 首版提供两种独立安装包，避免“Universal”包体和构建复杂度；后续可评估 `universal-apple-darwin`。
- 建议首期验证 macOS 13 及以上、维护者当前使用版本，以及拟支持的最新稳定版本。
- 最低版本是待验证产品承诺，不是仅凭 Tauri 配置就成立；必须考虑 WKWebView、插件、Rust 依赖、SDK 和实际测试。
- 若没有 Intel 设备或可用测试环境，标记“构建成功、运行未验证”，不能写成已全面兼容。

### 11.7 签名、公证与安装体验

三个概念必须分开：

| 概念 | 作用 | 是否因开源自动具备 |
| --- | --- | --- |
| 源码开源 | 他人可阅读、修改和构建代码 | 是，按仓库协议 |
| Developer ID 签名 | 证明分发者身份，保护签名完整性 | 否 |
| Apple 公证 | Apple 自动检查并提供可验证公证结果 | 否 |

公开分发建议流程：

1. 注册合适的 Apple Developer 账号，获取 Developer ID Application 证书。
2. 配置 Hardened Runtime 和最小 entitlements，签名 `.app` 及内部组件。
3. 根据 Tauri 当前官方文档构建待提交产物。
4. 使用 `notarytool` 或构建工具支持的公证流程提交。
5. 验证公证结果，按实际发布产物正确 staple 票据。
6. 在干净机器上下载正式产物，验证 Gatekeeper 和首次启动。

更新文件的应用级签名与 Apple 代码签名是不同机制，不能相互替代。个人开发本地运行无需先开通付费账号，但面向普通用户的无警告分发通常需要正式签名公证。

文档不建议用户全局关闭 Gatekeeper、关闭 SIP 或对不明来源应用批量清除 quarantine。个人测试优先从已审查源码构建；若使用 macOS 提供的单应用安全设置入口，应先验证来源和校验和，且行为依系统政策而定。

### 11.8 macOS 系统文本与双语打包

- 应用文件固定命名 `Salary Pulse.app`，应用内部标题按 locale 显示。动态修改应用包名会影响自启路径、更新识别与配置目录，不采用。
- 通过受支持的 Tauri 打包资源方式声明中文/英文应用本地化，必要时携带 `en.lproj`、`zh-Hans.lproj` 和 `InfoPlist.strings`；实施前验证系统语言列表识别和 Tauri 的资源映射。
- 运行时语言偏好由本地配置控制，不以 Finder 的文件名是否变成中文作为切换验收标准。
- 应用提供的菜单、窗口标题和新通知可以即时切换；Finder、权限提示、通知中心的系统元素可能受 macOS 缓存与系统语言控制，须明确这一边界。
- 所有本地化资源必须在签名、公证前加入 `.app`，发布后修改包内翻译会破坏签名完整性。测试断网时两种语言资源均存在。
- 通用品牌、应用标识、通知身份和自启标识不随 locale 变化，避免重复注册或两个菜单栏入口。

## 12. 安全、隐私与开源合规

### 12.1 默认隐私策略

- 薪资、排班、昵称仅留在本机，不默认网络传输。
- 默认没有分析 SDK、广告 SDK、崩溃上报或在线文案请求。
- 菜单栏默认显示倒计时而不是薪资。
- 系统通知默认只显示下班信息，不含金额和昵称。
- 调试日志不打印配置全文、薪资、访问令牌或导出内容。
- README 截图、自动化测试和 demo 使用固定的虚构数据。
- “隐藏金额”是视觉脱敏，不等于防截屏；首版不承诺系统级屏幕捕获保护。

### 12.2 本地数据保护

JSON 配置默认不加密，本地文件也不是绝对安全。本方案的首版保护边界是：本机账号权限、最小文件权限以及用户的 FileVault 等系统保护。

如果同一账号被他人使用、备份被公开或设备被攻破，本地明文数据可能被读取。因此不能宣传“数据在本地，所以绝对安全”。

- 若需要加密私人配置，P1 另行评估成熟的文件加密方案、Keychain 密钥保存和丢失恢复，不为了加密而先引入数据库。
- 如有更新密钥或未来 API 密钥，使用系统 Keychain 或 CI Secret，不存入普通 settings。
- 已提交到公开 Git 的秘密不能靠删除文件补救，必须轮换秘密。

### 12.3 Tauri 安全配置

- 主窗口、设置和悬浮窗分别配置 capability，遵循最小权限。
- 不启用任意 shell 执行，不暴露全文件系统读写能力。
- 所有 IPC 写入重复校验，不把前端校验视为安全边界。
- CSP 只允许打包资源；禁止运行时远程脚本、任意 iframe 和任意网页加载。
- 外部链接通过受限 opener 打开，只允许项目和官方文档等必要目标。
- 文件路径由后端固定，拒绝任意路径读写和路径穿越；JSON 使用结构化解析并验证大小、类型和字段。
- 自定义主题不能携带任意执行代码，导入资源不允许路径穿越。
- 网络核心功能关闭；P1 更新检查需要用户同意，并说明仅访问发布元数据，不发送薪资。

## 13. 性能与资源预算

### 13.1 运行策略

- Rust 每秒轻量重算当前快照，不每秒读写配置文件。
- 菜单栏文字最多约 10 秒刷新一次，状态切换和唤醒时立即更新。
- 主窗口金额每秒更新；如果开 4 位小数也不需要 60 次每秒计算金额。
- 角色可见且动态效果开启时，目标约 24～30 FPS；隐藏后停止动画。
- 隐藏所有 WebView 时只维护必要的原生时钟与提醒，不进行图形绘制。
- 窗口位置写入去抖，例如拖动结束或 500ms 稳定后保存。
- 文件写入集中于用户保存、必要恢复状态和通知去重，状态记录有数量上限。
- P1 若实现大范围历史重算，应在后台工作队列支持取消和进度；首版不为不存在的历史账本增加任务。

### 13.2 建议测量目标

以下是开发预算，不是当前已实现或所有设备保证：

| 指标 | 建议目标 | 测量要求 |
| --- | --- | --- |
| 冷启动到菜单栏可用 | 参考 Apple Silicon 设备约 2 秒内 | 至少重复 10 次，记录系统与设备 |
| 仅菜单栏运行 CPU | 一段稳定区间内平均约 1% 以下 | 定义采样工具和时长，不只看瞬时值 |
| 仅菜单栏总内存 | 争取低于约 150 MB | 包含主进程和 WebView 子进程 |
| 开主窗口与动画 | 不影响常用办公；先预算约 200 MB 内 | 活动监视器与 Instruments 实测 |
| 安装包大小 | 争取低于约 40 MB / 架构 | 取决于角色、音频和依赖 |
| 长期运行 | 8 小时无持续内存增长和重复监听 | 多次开关窗口、合盖和外接屏 |
| 配置保存 | 常规操作约 200ms 内有反馈 | 慢磁盘下正确显示保存中或失败 |

如果原生桥接或素材使预算超出，先测量主要消耗，再决定是否简化动画、销毁隐藏窗口或调整框架。不能仅凭“Tauri 比 Electron 轻”宣称续航没有影响。

### 15.3 重要性质断言

- 同一组规则和同一 `now` 必须生成相同金额，运行次数不影响结果。
- 将有效区间在任意时刻拆分，分段金额之和等于整体金额（最终舍入前）。
- 无薪区间越长，其他条件不变时估算不会增加。
- 固定班次的估算秒数不能超过计划有薪秒数。
- 正常墙钟前进、固定费率和固定班次下，金额非递减；时钟修正不适用这一断言。
- 同一通知事件重复处理不会再次提交。
- 已保留班次快照不受待生效薪资变化影响；缺失历史数据不伪造。

### 15.4 原生测试清单

- 安装后无需开发环境，断网首次配置并使用。
- 关闭主窗口后菜单栏仍可打开设置；`Cmd+Q` 后活动监视器无残留本应用进程。
- 反复启动不会出现多个菜单栏图标或重复通知。
- 通知拒绝、允许、系统后来关闭权限时状态正确。
- 自启开启、关闭、失败以及重启登录后的状态一致。
- 合盖、锁屏、唤醒、切换显示器后金额和窗口位置正常。
- 菜单栏深浅色、刘海屏和系统缩放下没有不可读文字。
- 外接屏拔出后悬浮窗回到可见位置。
- 隐私模式在全部窗口、菜单栏、通知和截图演示中一致。
- 大金额、最长允许昵称、4 位小数不挤出布局。
- VoiceOver、键盘操作、焦点可见和系统减少动态效果可用。
- 全屏和 Spaces 的限制被记录，没有承诺未验证行为。

- 任一架构 DMG 都支持离线切换两种语言，退出重开或替换新版不丢语言选择。

### 15.5 发布完成定义

P0 发布必须满足：功能验收、核心计算与配置格式升级测试、完整中英文文案与切换测试、原生测试记录、安装包标识、依赖/素材许可记录、双语安装说明、README 真实状态和已知限制。公开正式版的签名公证属于完成条件，不是任意推迟的增强功能。

“CI 绿色”不能替代签名、公证和干净机器安装验证；“构建出了 DMG”也不能替代双架构实际兼容性验证。

### 15.6 中英文专项验收

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| L01 | 首次启动中文/英文系统 | 按应用/系统首选语言选中支持 locale，无另一种语言闪屏 |
| L02 | 其他系统语言或无法读取 | 回退英文，语言控件仍可手动选中文 |
| L03 | 手动选择后重启、升级、断网 | 偏好保持，不被系统覆盖，不请求远程语言包 |
| L04 | 工作/午休/下班中切换 | 同一时刻金额、币种、时区、班次 ID 不变；定时和动画不重新开始 |
| L05 | 主窗口与悬浮窗同时打开 | 切换后两个窗口和原生菜单同步，新打开窗口读取最新语言 |
| L06 | 有未保存薪资草稿时切换 | 不丢草稿、不自动保存薪资；revision 冲突保留输入并提示 |
| L07 | 切换保存失败 | 仍用旧持久化偏好，明确本次失败，不宣称重启会保持新语言 |
| L08 | 切换后发送通知 | 新标题正文采用当前 locale，已有通知不重发 |
| L09 | 缺失 key、插值或复数形式 | CI 失败；运行时最终回退英文而不是裸 key |
| L10 | 英文长文、200% 文本缩放 | 按钮、设置、错误框和悬浮窗不裁切、不重叠，可访问名称正确 |
| L11 | 数字、货币、日期和时间 | 精确字符串舍入；输入歧义拒绝；24 小时班次规则明确；无隐式换汇 |
| L12 | 配置损坏或旧版没有语言字段 | 恢复入口双语可用；格式升级仅补语言默认，不改旧薪资 |
| L13 | 快速切换与乱序事件、system 模式系统语言变化 | 最新 localeSequence 有效，相同配置 revision 也能接收新语言；监听不泄漏 |
| L14 | 鼓励语与自定义昵称 | 内置同 ID 双语内容正确、冷却不重置；用户文字不自动翻译 |
| L15 | 原生翻译资源打包 | 菜单退出等完整翻译，OS 系统文本边界可解释；签名前包含两种语言 |

## 16. Mac 开发、构建与安装

本节是未来实现后的操作模板。当前只有文档，以下项目命令暂时不能直接运行成功。

### 16.1 开发者环境

需要：Git、满足依赖要求的 Node.js LTS 与 npm、Rust stable / Cargo、Xcode Command Line Tools。正式签名公证还需对应 Apple 证书和工具链。

检查命令：

```bash
git --version
node --version
npm --version
rustc --version
cargo --version
xcode-select -p
```

若未安装 Apple 命令行工具，可以运行 `xcode-select --install`，按系统界面完成；其余依赖按官方安装说明安装，不提供不明来源的一键 shell 安装脚本。

如使用 Homebrew 管理 Node.js，确认所选 LTS 版本与项目要求一致。Rust 通过官方 rustup 管理；项目可用 `rust-toolchain.toml` 记录已验证工具链。

### 16.2 从源码开发

```bash
git clone https://github.com/yuzhenhai0808/salary-pulse.git
cd salary-pulse
npm ci
npm run tauri -- dev
```

初次构建会下载 Rust 依赖并编译，明显慢于后续启动，网络限制下可能需要配置可信镜像。依赖安装不能访问私人薪资，运行应用后才会创建个人数据目录。

只预览界面：

```bash
npm run dev
```

该模式使用演示桥接，不验证菜单栏、权限、休眠、自启和本机配置读写。

### 16.3 本地质量检查

```bash
npm run typecheck
npm run lint
npm run check:locales
npm run test -- --run
npm run build
cargo fmt --manifest-path src-tauri/Cargo.toml --check
cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
cargo test --manifest-path src-tauri/Cargo.toml
```

以上命令分别运行，任一步失败都应修复或说明原因，不能继续发布并声称全部通过。

### 16.4 构建 Mac 安装包

发布安装包时显式选择 DMG；打包由维护者完成，不要求普通用户执行这些命令。当前架构：

```bash
npm run tauri -- build --bundles dmg
```

显式目标：

```bash
rustup target add aarch64-apple-darwin
npm run tauri -- build --target aarch64-apple-darwin --bundles dmg

rustup target add x86_64-apple-darwin
npm run tauri -- build --target x86_64-apple-darwin --bundles dmg
```

目标安装并不保证跨架构所有原生依赖都能编译；优先在对应 macOS runner 或实机完成构建与验证。构建产物通常在 Cargo target 的 `release/bundle/` 下，显式目标可能多一层目标目录；CI 应根据当前 CLI 输出取产物，不写死未经确认的路径。

### 16.5 面向普通用户的安装

1. 打开 GitHub Releases，按 Mac 芯片选择 Apple Silicon 或 Intel 版本。
2. 核对文件名、版本、发布者和 SHA-256 校验和。
3. 打开 DMG，把应用拖入“应用程序”。
4. 从“应用程序”首次打开并完成设置。
5. 下班提醒和开机自启按个人意愿开启。

不需要 Docker、终端常驻、云账号或启动开发服务器。应用安装后使用系统 WebView，不下载一个远程网页作为主界面。

公开 GitHub Releases 的附件通常无需登录即可下载；私有仓库则需要对应访问权限。应用不要求 GitHub 登录，也不把用户配置同步到 GitHub。

### 16.6 卸载与个人数据

- 先在应用里关闭自启并选择是否删除个人数据。
- 退出后移除 `.app` 即卸载程序主体。
- 未主动删除的数据目录保留，重新安装时可以继续使用。
- 文档给出通过系统界面寻找本应用数据的方式，不让用户对整个 `~/Library` 执行删除命令。
- 已导出的私人备份不由程序自动删除，用户需自行管理。

## 17. GitHub CI 与发布流程

### 17.1 持续集成

`ci.yml` 在 Pull Request 和主分支提交时执行：

1. Checkout，安装固定 Node.js 与 Rust 工具链。
2. 使用锁文件安装前端依赖。
3. TypeScript、lint、格式、双语资源完整性与前端单元测试。
4. 前端生产构建和中文/英文两个 locale 的浏览器 E2E。
5. Rust 格式、Clippy、领域和配置文件存储测试。
6. 至少在 macOS 构建一次桌面工程；按成本安排双架构检查。
7. 上传失败截图和测试结果，演示数据不含真实薪资。

普通 PR 不授予写 Releases 权限，也不提供签名密钥。来自 fork 的代码不能在带秘密的可信发布任务中执行。Actions 依赖固定到审核过的版本或 commit，避免使用含混的最新引用。

### 17.2 发布触发与矩阵

**第一阶段采用本机打包、手动发布，GitHub Actions 自动发布是后续可选优化，不是使用应用的前提。**

维护者手动发布流程：

1. 在 Mac 上实现和测试应用，按目标架构生成 DMG，正式面向用户时完成签名公证。
2. 检查安装包，生成校验和，确保包内没有维护者的真实薪资、配置或密钥。
3. 确认安装包构建所用 commit 已提交且与版本标签一致；如对源码或资源做了修改，需要重新构建和签名，不上传来源不明的旧包。
4. 在仓库 Releases 页面选择“创建新版本发布”，填写版本和说明。
5. 将 DMG 和校验和文件上传为 Release 附件（Assets），先保存草稿。
6. 完成下载和安装验证后正式发布，在 README 添加下载入口。

DMG 不提交进 Git 源码历史，也不通过 Git LFS 或 Issue 附件充当正式发布渠道。GitHub 页面自带的 `Source code (zip)` 是源码，不是 Mac 安装包。不要用需要登录且有保留期限的 Actions artifact 代替公开 Release 下载。

未来若实现自动发布，`release.yml` 由受保护版本标签，如 `v0.1.0`，或手动确认触发。

| 构建项 | 目标 | 产物名建议 |
| --- | --- | --- |
| macOS Apple Silicon | `aarch64-apple-darwin` | `SalaryPulse_0.1.0_macos_arm64.dmg` |
| macOS Intel | `x86_64-apple-darwin` | `SalaryPulse_0.1.0_macos_x64.dmg` |

GitHub runner 标签和架构会随平台调整；实施时查官方 runner 文档，不把某个 `macos-latest` 默认当作稳定的特定 CPU 架构。记录产物的实际架构，并在发布验证中检查。

矩阵只按 CPU 架构划分，不再按语言分包。Release 提供同一附件的中英文说明，README 与 README.en.md 互链。发布检查记录版本、源码 commit、架构、最低 macOS、构建工具版本、SHA-256、签名/公证结果及两种语言安装测试；所有翻译资源改动必须在最终签名前完成。

版本号在 `package.json`、Tauri 配置、Cargo package 和 tag 中保持一致，由校验脚本检查。不要仅修改前端版本而让安装包仍显示旧版。

### 17.3 正式发布流水线

```text
版本提交与受保护标签
  → 质量检查
  → 双架构构建
  → Developer ID 签名
  → Apple 公证与票据验证
  → DMG 与校验和
  → Draft GitHub Release
  → 人工安装验收
  → 发布正式 Release
```

没有签名资格的个人开发构建应明确标记开发/测试用途，不能包装成已公证正式版。

发布说明含新增功能、修复、支持系统、架构、计算口径变化、配置格式升级提示和已知限制，并提供中英文安装摘要。每个产物生成 SHA-256，例如在确定目录内使用 `shasum -a 256 <明确产物文件>`，不把私人文件放入批量校验范围。

### 17.4 CI 密钥

可能需要的秘密包括 Developer ID 证书与密码、公证认证凭据、后续更新私钥。具体环境变量名称依据使用的 Tauri 版本和官方签名文档设置。

- 存 GitHub Actions Secrets / Environment Secrets，不进入源码。
- 发布 environment 设置人工审批和受保护分支或标签。
- 最小化 `GITHUB_TOKEN` 权限，仅发布任务允许写 Releases。
- 密钥不用于普通 CI、fork PR 或 `pull_request_target` 中执行不可信代码。
- 临时签名 keychain 的创建和清理只作用于 CI 临时环境。

### 17.5 更新策略

P0：用户手动下载新版，安装替换 `.app`，保留本地 JSON 配置，新程序按需升级文件格式。

P1：可选检查 GitHub Releases 元数据并提示下载，不强制联网、不上传薪资。

P2：若使用 Tauri updater，需要另外生成插件要求的更新包、元数据和更新签名。DMG 本身不自动等于可用更新产物。必须验证双架构、失败回滚、旧配置兼容、签名轮换和服务器不可用时应用继续离线运行。

## 19. 主要风险与应对

| 风险 | 可能表现 | 应对 |
| --- | --- | --- |
| 工资口径不清 | 用户认为金额等于真实到账 | 所用参数显式展示，估算标签、示例与测试先行 |
| 定时器累加 | 休眠、隐藏或重启后数字错误 | 按时间区间重算，Rust 唯一权威 |
| 改薪改变当前班次 | 当前显示突然跳变 | 下一班次生效、少量班次规则快照，不建立无限版本库 |
| 夜班与日界线 | 午夜重复计薪或漏计 | 锚定日期与自然日分开，半开区间 |
| 假定所有地区无 DST | 部分时区排班无法解析 | chrono-tz，明确重复/不存在时刻规则 |
| 原生能力预期过高 | 悬浮窗不能覆盖某些全屏空间 | 先做技术验证，记录支持边界 |
| 常驻耗电 | 风扇或续航下降 | 隐藏停动画，低频菜单刷新，实测资源 |
| 没有签名公证 | 普通用户安装受阻 | 个人源码运行与正式发布区分，提前准备证书 |
| 双架构只编不测 | Intel 包能产出但打不开 | 对应环境验收，未测试明确标注 |
| 多窗口重复计时 | 金额或通知翻倍 | 单 Rust 服务、快照共享、单实例和持久化去重 |
| 通知可靠性误称 | 休眠/专注模式下漏发 | 写清能力边界，不承诺恰好一次或退出后提醒 |
| 私人薪资泄露 | 日志、截图、Issue 或备份公开 | 默认脱敏，演示数据，导出确认，最小日志 |
| 第三方素材无授权 | 开源发布或商业使用纠纷 | 原创资产，逐项记录许可，不直接复制 |
| 配置保存或升级失败 | 新版打不开或丢配置 | 临时文件替换、有效备份、降级保护与故障测试 |
| 功能不断膨胀 | 开发成大型效率平台 | 固定 P0，扩展按使用反馈逐项评估 |
| 双语仅翻译 React | 菜单/通知还是中文，用户无法彻底切换 | 共享资源、原生 locale 服务、L01～L15 验收 |
| 语言改变计薪 | 切英文变美元或改变时区、重复通知 | locale 与业务规则 ID 隔离，机器码契约与测试 |

### 21.2 最终建议

建议把首版定义为：**Tauri 2 + React + TypeScript 界面，简体中文/英文即时切换，Rust 单一计薪引擎，本机 JSON 配置与少量状态文件，菜单栏和可选悬浮窗，原创 2D 角色，下班提醒与双语 DMG 安装包。不引入数据库。**

最先开发的不是复杂动画，而是可验证的排班和时间区间规则，以及菜单栏、休眠和窗口行为的小型技术验证。随后补齐个性化和趣味反馈，确保成品仍然是“鼓励器”，而不是只有数字的计时面板。

最终交付应让普通用户从 GitHub Releases 下载并安装，也让开发者通过锁定依赖和清晰文档从源码构建；同时明确估算收入、隐私、未验证兼容性和签名状态，不用“开源”替代可靠的 Mac 分发体验。

最初可由维护者在本机打包并手动上传到 Releases；用户下载安装后，配置和数据独立保存在各自 Mac 上。自动构建发布只是维护便利功能，不改变这一使用方式。

### 22.2 仍需在编码前确定或验证

- **最低系统与 CPU 范围**：macOS 13+ 是暂定目标，需确认你的设备和 Intel 测试环境；没有验证的版本不宣传为正式支持。
- **Apple 签名资格**：确认是否已有 Developer ID 账号/证书；没有时先个人测试，不能承诺普通用户无警告安装。
- **原生本地化与菜单体验**：验证应用级语言读取、Tauri 原生菜单更新、WKWebView 与 `lproj` 打包；系统权限窗口不是应用可任意改写的内容。
- **趣味互动的具体动作**：首版确认一个动作的触发、持续时间、冷却、结束状态和素材验收，避免“至少一项互动”到实现时仍无具体设计。默认建议点击鼓励，短时欢呼后返回工作/休息基础状态。
- **配置恢复故障实验**：文件安全写入不能取代验证；必须在两个文件不同提交阶段模拟崩溃、损坏、磁盘不可写、旧备份恢复和升级失败。
- **原生能力与耗电**：菜单栏、悬浮窗多屏定位、合盖唤醒、8 小时资源观察仍需实机验证，浏览器 E2E 无法覆盖。
- **英文人工校对**：确认产品术语和幽默语气；自动缺键检查只能检查完整性，不能证明翻译自然或没有歧义。

### 22.3 可以后置，不必增加首版复杂度

数据库、服务器、云同步、历史薪资版本库、自动翻译平台、自动更新和多语言主题商店均不是首版所需。首版只交付同一应用内完整中文/英文体验、本机配置和可安装 DMG。
